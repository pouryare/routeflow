Production build (`next build` + `next start`), 4-core / 16 GB container, **smoke-scale** demo data
(`npm run seed:demo -- --scale=smoke`, 7 MB). Timings from `scripts/perf/timing.mjs`; warm = median of 5.
The heavy dataset (`--scale=heavy`) takes over 45 minutes to seed here and was not ready; **these numbers
say nothing about behaviour at scale** and the whole table should be re-run on heavy data.

## Reading
- At smoke scale the server is not the bottleneck. Only the **owner dashboard (182 ms)** and the
  **accounting journal (121 ms)** stand out, and both are the two things the plan already flags as unbounded
  (`salesDashboard` loads every delivered line; the journal has no `LIMIT`). Both will grow with data.
- Cold CRM (292 ms) is first-hit cost (route + prepared statements); warm is 31 ms.
- Therefore a user-visible 2-3 s is **not** explained by server render time on small data. Candidates to test
  next: heavy data, `next dev` compilation, first-load JS size, and client-side work after navigation.

## What was actually wrong (none of it was what the original ChatGPT-style advice targeted)

1. **Startup hang.** `getDb()` on this database did not finish in over 2 minutes (now 0.6 s). Boot-time
   backfills ask, for every row, "has this already been posted?" using `NOT EXISTS` subqueries on
   `journals(source_type, source_id)`, `stock_movements(ref_type, ref_id, kind)`,
   `delivery_line_batches(order_line_id)` and `batches(purchase_line_id)`, none of which were indexed.
   The same journal lookup guards every payment and sale posting, so *every write slowed with ledger size*
   (the heavy seed's orders phase took 29 minutes).
2. **Missing indexes elsewhere:** `payment_allocations(payment_id)` (debt pass scanned the table once per
   payment), `journals(reverses_journal_id)` (the journal page scanned once per row),
   `stock_movements(product_id, ...)` (stock summed by scanning every movement per product).
3. **N+1 queries:** customer health (6 queries per customer, run twice per dashboard load), CRM view counts
   (one query per view), journal legs (one per journal), commission ledgers (one line query per order,
   hundreds of thousands per load).
4. **Loading every order line into JS** for dashboard and debt figures (now aggregated in SQL).
5. **The same whole-org computations repeated within one request** (debt three times, each salesperson's
   accruals once per group manager).

## Verification that numbers did not change
- Whole-org debt: equal to the original row-by-row implementation (kept as `tests/helpers/legacyDebts.ts`)
  for all 700 customers; also covered by a fixture test with half-Toman rounding, partial and voided payments.
- Customer health: batched equals per-customer for every row (`tests/health-repo.test.ts`).
- Commission statements (sales, driver, manager; month, August, year; 8.5 MB of output): byte-identical.
- `salesDashboard` for five roles: 1,364 values identical, 25 kilogram values within 1e-9 (SQLite sums floats
  with compensation; the old code summed naively), no ranking changed.

## Streaming note
Next streams a Suspense boundary only if the server returns to the event loop. All reads here are synchronous
`node:sqlite`, so the slow sections `await yieldToEventLoop()` (a 75 ms timer; 0 ms does not work, measured:
shell + slow part arrive together at 1.8 s with 0 ms, shell at ~90 ms with 50 ms).

## Not done, and why
- **Precomputed/snapshot dashboard figures (plan Task 6):** not needed after the above; would add staleness to
  money screens.
- **`force-dynamic` audit (Task 7):** no change. Every page that sets it reads cookies directly or through a gate,
  so it is dynamic regardless; the export is redundant but harmless. It only needs to go if Cache Components is
  ever enabled (Next removes `dynamic` then).
- **Commission lifetime accrual** still walks every order a person ever sold (a floating-point kilogram sum that
  I would not reorder on payroll numbers). It now runs once per request instead of ~6 times. If it becomes the
  bottleneck, the next step is a stored per-order weight, which is a schema change.
- **Dashboard `/sales/dashboard` for the owner is still 2.7 s end to end**; most of it is that commission walk
  and stock/analysis, now streamed after the first content.
