# Performance baseline, 2026-10-20

Production build (`next build` + `next start`), 4-core / 16 GB container, **smoke-scale** demo data
(`npm run seed:demo -- --scale=smoke`, 7 MB). Timings from `scripts/perf/timing.mjs`; warm = median of 5.
The heavy dataset (`--scale=heavy`) takes over 45 minutes to seed here and was not ready; **these numbers
say nothing about behaviour at scale** and the whole table should be re-run on heavy data.

## Build blockers found and fixed first
`next build` failed at HEAD, so there was no production build to measure. Two client-bundle leaks that
`next dev` tolerates: `sales/admin/holidays/page.tsx` (client page importing the async server `PageHeader`)
and `UnloadTapFlow` (client component importing constants from `lib/repo/unload`, which pulled in `node:sqlite`).

## phone_sales (`demo.sales`)
Fast everywhere it is allowed (dashboard 98 ms warm, everything else under 30 ms). `/leads`, `/accounting/*`
return 307: the role is redirected away, so those rows are not measurements.

## Reading
- At smoke scale the server is not the bottleneck. Only the **owner dashboard (182 ms)** and the
  **accounting journal (121 ms)** stand out, and both are the two things the plan already flags as unbounded
  (`salesDashboard` loads every delivered line; the journal has no `LIMIT`). Both will grow with data.
- Cold CRM (292 ms) is first-hit cost (route + prepared statements); warm is 31 ms.
- Therefore a user-visible 2-3 s is **not** explained by server render time on small data. Candidates to test
  next: heavy data, `next dev` compilation, first-load JS size, and client-side work after navigation.
